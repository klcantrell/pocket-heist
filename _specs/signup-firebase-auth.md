# Spec for Signup Firebase Auth

branch: claude/feature/signup-firebase-auth

## Summary

- Wire the existing SignupForm component to Firebase Authentication using the Firebase web SDK
- On successful signup, generate a random display name (codename) by picking one word from each of three distinct word lists and combining them in PascalCase
- Set the generated codename as the Firebase user's `displayName`
- Create a document in a Firestore `users` collection storing only the user's `uid` and `codename` (no email)

## Functional Requirements

- The signup form submits email and password to Firebase Auth via `createUserWithEmailAndPassword` using the `auth` export from `lib/firebase.ts`
- After successful account creation, a codename is generated by selecting one random word from each of three separate word lists (e.g., adjectives, animals, actions — or similar thematic sets) and joining them in PascalCase (e.g., `SilentFoxDashes`)
- The codename is set as the user's `displayName` via `updateProfile`
- A new document is created in the Firestore `users` collection (using the `db` export from `lib/firebase.ts`) with the user's `uid` as the document ID, containing only `codename` and `id` fields — the email must NOT be stored
- Only the Firebase web SDK (`firebase/auth`, `firebase/firestore`) is used — no Firebase Admin SDK or server-side calls
- Form validation errors and Firebase auth errors (e.g., email already in use, weak password) are displayed to the user
- On successful signup, the user is redirected to the dashboard (the existing AuthContext should pick up the new auth state)

## Possible Edge Cases

- Email already registered with Firebase — display a user-friendly error
- Weak or invalid password — display Firebase's error message in a readable way
- Network failure during signup, profile update, or Firestore write — handle gracefully
- Codename collision in Firestore (unlikely but possible) — acceptable to ignore for now since codenames are not unique constraints
- User closes the page after auth creation but before Firestore document is written — the user exists in Auth but has no Firestore document; the app should handle missing user documents gracefully

## Acceptance Criteria

- Submitting the signup form with valid email and password creates a new Firebase Auth user
- The created user has a randomly generated PascalCase `displayName` composed of three words from three distinct word lists
- A Firestore document exists at `users/{uid}` with `id` and `codename` fields and no email field
- Auth errors are surfaced to the user in the form UI
- After successful signup, the user is redirected to the authenticated dashboard area
- All Firebase operations use only the web SDK client-side

## Open Questions

- What themes should the three word lists follow (e.g., adjective-animal-verb, color-object-action)? Defaulting to a fun heist-themed set unless specified. adjective-animal-verb.
- How many words should each list contain? A reasonable default (15-25 per list) gives thousands of unique combinations. Let's do 10 for now.
- Should the signup button show a loading/disabled state during the async operation? Yes.

## Testing Guidelines

Create a test file(s) in the ./tests folder for the new feature, and create meaningful tests for the following cases, without going too heavy:

- Codename generation produces a PascalCase string composed of exactly three words
- Codename generation picks from three distinct word lists
- Generated codenames have reasonable randomness (multiple calls produce different results)
- Form displays error messages when signup fails
- Form fields are accessible with proper labels
